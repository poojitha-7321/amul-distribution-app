# Dairy Order Desk: Distributor & Retailer Order Management

Order management and inventory for a milk and curd distributor. Retailers place next-day orders from their phones; the distributor accepts, prepares and delivers them, and stock is reserved and deducted automatically.

- **Works on Android and iOS** as an installable web app (PWA). No app-store account needed.
- **Free to host**: one Render free web service plus a free Neon PostgreSQL database.
- **Scope**: milk and curd products only (categories are editable).

## Features

| Retailer (mobile-first) | Distributor (responsive console) |
|---|---|
| Own secure login, forced password change on first login | Dashboard cards: retailers, orders today, awaiting processing/delivery, delivered today, low stock |
| Browse by category, search, choose pack size and packet/crate, +/- quantity | Orders table with filters (date, retailer, status, delivery status) and detail page |
| Cart review, delivery date, notes, one-tap submit (double-submit safe) | Accept, reject, prepare, ready, confirm full or partial delivery, cancel |
| Live order status timeline, delivered vs ordered quantities | Retailer accounts: create, edit, deactivate, reset password |
| Order again (one click), frequently ordered, cancel when allowed | Product and variant management, pack sizes, crate conversion, prices |
| In-app notifications | CSV/Excel import (catalogue and stock, with preview, fix and error report) |
| Can never see another retailer's data | Inventory, adjustments with reasons, returns and damage, movement history, low-stock alerts, 10 reports with CSV/Excel export, audit log |

### Inventory policy (how stock works)

1. **Submit**: nothing is deducted. Retailers cannot order more than is available (the default *block* policy), or can if you choose the *allow* policy in Settings.
2. **Accept**: stock is **reserved** (`available = physical − reserved`). If not enough is available, the accept is refused and nothing is reserved. The *allow* policy reserves whatever is available instead.
3. **Cancel / reject**: reservations are released.
4. **Confirm delivery**: physical stock drops by the **delivered** quantity (e.g. 18 of 20), and the unused reservation is released. The order becomes *Delivered* or *Partially delivered*, and the shortfall is recorded.
5. Returns, damage and manual corrections are separate transaction types, each needing a reason, and each is written to the audit log.

Safety: stock rows are locked inside a database transaction, so simultaneous orders cannot oversell. Each order has one delivery record, so a delivery cannot be confirmed twice. Database CHECK constraints (`physical ≥ 0`, `reserved ≤ physical`) are the last line of defence.

## Run locally

Requires Node.js 20+. **No PostgreSQL or Docker install is needed**: a real PostgreSQL is downloaded as an npm package for development.

```bash
npm install
npm run dev:db        # terminal 1: starts a local PostgreSQL on port 54329 (keep running)
npm run migrate       # terminal 2: create tables
npm run seed          # demo admin, 3 retailers, sample milk & curd catalogue, sample orders
npm run dev:server    # API on http://localhost:4000
npm run dev:client    # app on http://localhost:5173 (proxies /api to the server)
```

To run it like production (one process serving the built app): `npm run build && npm start`, then open http://localhost:4000.

## Deploy for free (Render + Neon)

1. **Database**: create a free project at https://neon.tech and copy its connection string (`postgres://…?sslmode=require`).
2. **Code**: push this repo to GitHub (done if you are reading this there).
3. **Web service**: at https://render.com choose *New → Blueprint*, select this repo. `render.yaml` configures everything. Set:
   - `DATABASE_URL`: the Neon connection string
   - `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` (min 10 chars): your first admin login
   - `JWT_SECRET` is generated automatically.
4. Deploy. Migrations and the first-admin creation run on every start (both are idempotent). Open the Render URL and log in.
5. Optional: set `SEED_SAMPLE_CATALOG=true` for the first deploy to load the sample milk/curd list, then replace it with your real products via **Import**.

Notes on the free tier: Render free services sleep after ~15 minutes idle, so the first request after a pause takes about 30 seconds. Neon's free tier suspends idle databases and wakes them automatically. For a busy distributor, the cheapest paid Render instance removes the sleep.

## Push notifications

Admins get a push when a retailer places an order (and on low stock); retailers get one when their order status changes. It uses standard Web Push (VAPID), so it is free and needs no third-party service.

1. Generate keys once: `npx web-push generate-vapid-keys`.
2. In Render set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` (e.g. `mailto:you@gmail.com`). Keep the private key secret.
3. On each device, log in, open the bell and tap **Turn on push alerts**.

Android Chrome and installed PWAs work. iPhone needs iOS 16.4+ and the app added to the Home Screen first. For an Android APK that supports push, build the Trusted Web Activity in `twa/` (see `twa/README.md`); the Capacitor app in `client/android` uses a WebView and cannot receive Web Push.

## Android APK

- **With push notifications (recommended):** `twa/`, a Trusted Web Activity built with Bubblewrap. Needs JDK 17 and the Android SDK. Steps are in `twa/README.md`.
- **Plain WebView app (no push):** `client/android`, a Capacitor project: `cd client && npm run android:sync && cd android && .\gradlew.bat assembleDebug`. Output: `client/android/app/build/outputs/apk/debug/app-debug.apk`.
- **No tools at all:** https://www.pwabuilder.com can package the live site (tick notification delegation).

Never commit keystores or passwords.

## Replacing the sample catalogue

The seeded products, pack sizes, crate sizes and prices are **samples**. Verify your actual Amul SKUs, pack sizes, crate sizes and rates for your territory, then:

1. Admin → **Import** → download the template → fill in your list → upload → fix any flagged rows → import.
2. Admin → **Import → Stock quantities** → load opening stock (explicit confirmation and reason required).
3. Deactivate the sample products you do not supply (Admin → Products).

Catalogue imports never create or change stock; stock changes go only through the stock workflow.

## Assumptions

- Orders are for **next-day delivery or later** (up to 14 days ahead, configurable). The business timezone is `Asia/Kolkata` (`APP_TIMEZONE`).
- Stock is counted in whole units of the variant's stock unit (usually packets). A crate is a configured multiple per variant (`units_per_crate`); stock is always stored in the base unit.
- Delivery confirmation **closes** the order: any undelivered balance is released, not kept open for a later partial delivery. Create a new order for the balance.
- Prices are optional. Totals are always recalculated on the server; the browser's numbers are never trusted. Order lines snapshot product name, SKU, pack and price.
- Retailer login accounts are created by the distributor (no self-registration). Password reset is by the distributor, with a one-time temporary password.

## Known limitations

- Notifications are in-app (a bell, refreshed every 30 s). There is no push, SMS or email yet.
- Fractional quantities (e.g. 2.5 kg) are not supported; use the pack-based units.
- One login per retailer shop at creation time (more users can be added in the database; a UI for this is not built).
- Product images are by URL only (placeholder emoji otherwise); there is no file upload.
- No online payment or invoicing (amounts are informational).
- The PWA needs a connection to place orders; only the app shell is cached offline, since stock and orders must be live.
- Rate limiting is per server process (fine for a single free instance).
